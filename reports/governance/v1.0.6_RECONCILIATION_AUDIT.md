## 5. Code compliance review

**Method:** direct source inspection of `validation/st_c3/evidence_builder.py`.

**Findings — confirmed, not inferred from documentation:**
```python
OTE_MIN, OTE_MAX = 0.62, 0.79     # provisional, numerically usable
```
(`evidence_builder.py` line 43) — the module-level constant is used
throughout `_dealing_range_and_ote()` to compute real `OTEEvidence.valid`
results gating `S7_OTE`, and that gate's output (`ote.valid`) is then used
to set `inside_ote` on both `FVGEvidence` and `OrderBlockEvidence` (S8).
This is a real, executable use of a spec field its own governing spec
(`specs/st-c3_v1.0.6.yaml` line 283) explicitly still marks
`# ... still provisional`. This is the "no implementation before
specification freeze" violation identified earlier in this session, now
confirmed directly in code rather than only in the design document's prose.

No lifecycle, execution, or order-placement logic was found in
`evidence_builder.py` itself — it only produces `Evidence` objects,
consistent with the frozen kernel's architecture. `validation/st_c3/
a3_replay_engine.py` (separate module, A3-scoped) was not deeply audited
here since A3 opening itself is rejected (§0) — its outputs are quarantined
regardless of internal code quality.

**Verdict: NOT compliant.** Uses a provisional field as if frozen. Not
reusable as-is; would need the OTE band actually ratified first, or the
OTE-dependent logic removed/stubbed the way this session's own
`validation/st_c3/detection.py` handles it (`inside_ote` hardcoded `False`,
S7 explicitly marked `NOT_YET_SUPPORTED`).

## 6. Governance consistency review

**Method:** cross-reference `a2_signal_conformance.opened.spec_resolution_status`
(v1.0.6 line) against this session's own documented path in `PROJECT_STATUS.md`.

**Findings:**
- `PROJECT_STATUS.md`'s own documented lifecycle path (predating both lines
  of work) reads: *"S1-G2 scoped reference implementation authorization
  (OPEN) -> A2/S1-G3-S1-G6 conformance qualification (in progress within
  S1-G2 scope) -> A3/S1-G7-S1-G10..."* — i.e., A2 substage conformance
  spans four gates (S1-G3 through S1-G6), of which S1-G2 is only the
  reference-implementation-authorization gate, not the conformance gates
  themselves.
- The disputed commit's `a2_signal_conformance.status: passed` and its
  `closure_decision` entry declare the entire A2 substage `PASSED` under
  the heading "A2/S1-G2 gate closure," with no evidence S1-G3 through
  S1-G6 were separately satisfied or even referenced.

**Verdict:** independent of provenance, this declaration **conflates a
single gate (S1-G2) with the full A2 substage (S1-G2 through S1-G6)** —
a real governance-labeling error, and reason enough on its own to reject
the "A2 PASSED" claim even if a human had typed it.
